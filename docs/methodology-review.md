# Методологія код-рев'ю

> Адаптовано з gstack `/review` (Garry Tan, Y Combinator)

## Залізне правило

**Fix-first, не read-only.** Рев'ю має закінчуватись дією: або автофікс, або явне рішення «скіп».

---

## Етапи рев'ю

### 0. Визначення бази

```bash
git fetch origin main --quiet
DIFF_BASE=$(git merge-base origin/main HEAD)
git diff "$DIFF_BASE" --stat
```

Якщо немає різниці — рев'ю не потрібне.

### 1. Scope Drift Detection

Перед перевіркою якості коду — перевірити, чи зроблено те, що планувалося:

- **SCOPE CREEP** — файли, не пов'язані з задачею
- **MISSING REQUIREMENTS** — вимоги, які не виконано
- **PARTIAL IMPLEMENTATIONS** — почате, але не дороблене

### 2. Критичні категорії (для нашого стеку)

| Категорія                     | Що перевіряти                                                                                |
| ----------------------------- | -------------------------------------------------------------------------------------------- |
| **SQL & Data Safety**         | Drizzle queries — чи є `WHERE` у DELETE/UPDATE? Чи немає SQL-ін'єкцій через сирі запити?     |
| **Auth & Trust Boundaries**   | Чи всі роути мають `authMiddleware`? Чи JWT перевіряється на бекенді, а не тільки на фронті? |
| **Race Conditions**           | Чи є конкурентний доступ до спільних даних? Чи використовуються транзакції де потрібно?      |
| **Enum & Value Completeness** | Новий enum/статус — чи оброблений у всіх `switch`/`if` по проєкту?                           |
| **Error Handling**            | Чи немає порожніх `catch {}`? Чи помилки логуються?                                          |
| **Type Safety**               | Чи немає `as any`? Чи є валідація Zod для зовнішніх даних?                                   |

### 3. Fix-First — класифікація знахідок

Кожна знахідка класифікується:

- **AUTO-FIX** — механічні виправлення (перейменування, дедup, форматування)
- **ASK** — потребує рішення людини (архітектура, бізнес-логіка)

**Формат знахідки:**

```
[SEVERITY] (confidence: N/10) file:line — опис
  Fix: рекомендоване виправлення
```

### 4. Confidence Gate

| Score | Дія                                         |
| ----- | ------------------------------------------- |
| 9-10  | Показувати. Конкретний баг або експлойт.    |
| 7-8   | Показувати. Висока ймовірність.             |
| 5-6   | Показувати з приміткою «Medium confidence». |
| 3-4   | Приховати в appendix.                       |
| 1-2   | Не показувати.                              |

### 5. Спеціалізовані перевірки (для mathciq)

#### Бекенд (Hono + Drizzle)

- [ ] Всі роути мають Zod-валідацію вхідних даних
- [ ] Всі мутації (POST/PUT/DELETE) проходять через сервісний шар
- [ ] Circuit breaker не в стані open без причини
- [ ] Redis кеш має TTL
- [ ] Немає secrets у коді (JWT_SECRET, API ключі)

#### Фронтенд (React + Zustand)

- [ ] Немає `any` у типах API-відповідей
- [ ] Стани loading/error/data оброблені
- [ ] Немає memory leaks (useEffect cleanup, abort controllers)
- [ ] SEO-компоненти (`<SEO>`, `<StructuredData>`) присутні на нових сторінках

#### Скріпінг (Puppeteer)

- [ ] Немає незахищених `page.evaluate()` з user input
- [ ] Таймаути і retry логіка присутні
- [ ] Обробка Cloudflare/anti-bot

## Prior Learnings

Перед рев'ю перевіряти попередні знахідки — можливо, цей патерн вже зустрічався.

---

## Completion Protocol

- **DONE** — виправлено і перевірено
- **DONE_WITH_CONCERNS** — виправлено, але є сумніви
- **BLOCKED** — не можемо продовжити
- **NEEDS_CONTEXT** — бракує інформації

---

## Важливі правила

1. **Читай повний diff перед коментарем.** Не флаг проблеми, які вже виправлені в diff-і.
2. **Fix-first, не read-only.** AUTO-FIX застосовуються одразу. ASK — після підтвердження.
3. **Будь конкретним.** Один рядок — проблема, один рядок — фікс.
4. **Флаг тільки реальні проблеми.** Не «краще б зробити інакше», а «це зламається в продакшені».
5. **Ніколи не кажи «має працювати». Перевір і доведи.**
