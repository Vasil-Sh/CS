# Методологія дебагінгу

> Адаптовано з gstack `/investigate` (Garry Tan, Y Combinator)

## Залізне правило

**ЖОДНИХ ФІКСІВ БЕЗ ROOT CAUSE INVESTIGATION.**

Фіксити симптоми — це whack-a-mole. Кожен фікс, що не адресує root cause, робить наступний баг важчим для пошуку. Знайди причину, потім фікси.

---

## Фаза 1: Root Cause Investigation

### 1. Збери симптоми

- Прочитай повідомлення про помилку, стек-трейс, кроки відтворення
- Якщо недостатньо контексту — **запитай, але тільки ОДНЕ питання за раз**

### 2. Прочитай код

- Пройди шлях від симптому назад до потенційних причин
- Використовуй Grep для пошуку всіх посилань, Read для розуміння логіки

### 3. Перевір нещодавні зміни

```bash
git log --oneline -20 -- <affected-files>
```

Працювало раніше? Що змінилося? Регресія → причина в diff-і.

### 4. Відтвори

Можеш стабільно відтворити баг? Якщо ні — збери більше доказів.

### 5. Сформулюй гіпотезу

Конкретне, перевірюване твердження: що зламано і чому.

---

## Фаза 2: Pattern Analysis

Перевір, чи баг відповідає відомому патерну:

| Патерн                  | Сигнатура                                | Де шукати (для mathciq)                                  |
| ----------------------- | ---------------------------------------- | -------------------------------------------------------- |
| **Race condition**      | Нестабільний, залежить від таймінгу      | `backend/src/services/` — конкурентний доступ до БД      |
| **Null propagation**    | `Cannot read properties of undefined`    | `src/components/` — відсутні guards на optional значення |
| **State corruption**    | Некоректні дані, часткові оновлення      | `src/stores/appStore.ts` — Zustand, кеш                  |
| **Stale cache**         | Показує старі дані, фікситься очищенням  | `backend/.cache/`, Redis, localStorage SWR               |
| **Integration failure** | Таймаут, неочікувана відповідь           | Scraper (Puppeteer), AI API (DeepSeek/Gemini)            |
| **Configuration drift** | Працює локально, падає на Railway/Vercel | `.env`, Railway variables, Vercel env                    |

### Додаткові перевірки:

- Рекурентні баги в тих самих файлах → **архітектурна проблема**, не випадковість
- Пошукай в інтернеті: `"{component} {sanitized error} {framework}"`
- Перевір `git log` на попередні фікси в цій області

---

## Фаза 3: Hypothesis Testing

### Перед написанням будь-якого фіксу:

1. **Підтверди гіпотезу** — додай тимчасовий `console.log`, assertion, або debug output
2. **Якщо гіпотеза хибна** — повернись до Фази 1. Не вгадуй.

### Правило 3 страйків

**Якщо 3 гіпотези провалилися — СТОП.**

```
3 гіпотези перевірено, жодна не підтвердилась.
Це може бути архітектурна проблема, а не простий баг.

A) Продовжити — я маю нову гіпотезу: [опис]
B) Ескалювати — потрібна людина, яка знає систему
C) Додати логування і чекати — інструментувати область
```

### Червоні прапорці

- «Швидкий фікс» — немає «на потім». Фікси правильно або ескалюй.
- Фікс до того, як пройшов data flow — ти вгадуєш.
- Кожен фікс відкриває нову проблему — **не той рівень абстракції**.

---

## Фаза 4: Implementation

Коли root cause підтверджено:

1. **Фікси root cause, не симптом.** Мінімальна зміна, що усуває проблему.
2. **Мінімальний diff:** мінімум файлів, мінімум рядків.
3. **Напиши регресійний тест:**
   - Падає без фіксу → тест осмислений
   - Проходить з фіксом → фікс працює
4. **Запусти повний тест-сьют:**
   ```bash
   cd backend && pnpm test
   # або
   pnpm test
   ```
5. **Якщо фікс зачіпає >5 файлів** → STOP, запитай про blast radius.

---

## Фаза 5: Verification & Report

### Свіжа верифікація

Відтвори оригінальний сценарій багу і підтверди, що виправлено. Це не опціонально.

### Debug Report

```
════════════════════════════════════════
Symptom:         [що бачив користувач]
Root cause:      [що насправді було зламано]
Fix:             [що змінено, з file:line]
Evidence:        [тест-вивід, підтвердження фіксу]
Regression test: [file:line нового тесту]
Related:         [пов'язані TODO, попередні баги]
Status:          DONE | DONE_WITH_CONCERNS | BLOCKED
════════════════════════════════════════
```

---

## Важливі правила

1. **3+ невдалих фікси → STOP.** Проблема в архітектурі, не в гіпотезі.
2. **Ніколи не застосовуй фікс, який не можеш верифікувати.**
3. **Ніколи не кажи «має спрацювати». Верифікуй. Запусти тести.**
4. **Фікс >5 файлів → запитай дозвіл.**
5. **Completion status:**
   - DONE — причина знайдена, фікс застосовано, регресійний тест написано
   - DONE_WITH_CONCERNS — виправлено, але не можна повністю верифікувати
   - BLOCKED — причина неясна після розслідування

### Що робити з learning-ами після дебагу

Після кожного розслідування — занотувати в `docs/learnings.md`:

- Що було зламано
- Чому
- Як знайшли
- Які файли зачеплені
- Як фіксанули

Це зробить наступний дебаг швидшим — бо патерни повторюються.
